This Website

User Experience Web Development
Role Designer / Developer
Timeline June 2026 – Present
Tools Netlify, Git, Claude, Claude Code, HTML, CSS, Javascript

Overview

For the past 3 months, I sought to eliminate my need for Squarespace as a platform for my portfolio, as I've utilized the service on and off for many years but it was never what I truely wanted.

Problem #1: Squarespace is an expensive recoccuring charge and specific features are gated behind a more expensive tier.

Problem #2: I don't know much about web development

Solution

Solution #1: Replace Squarespace subscription with Anthropic subscription to establish a workflow Claude and utilize Claude Code to construct the portfolio which reflects my designs via Figma, of which will reflect my design principles.

Solution #2: Have fun in the process, and learn through fun.

.LANG-ing the Foundations

Not being a web-head by trade, I knew I was going to get myself caught in the sticky webbing of setup. I spent time inquiring about scalability, performance, and accessibility principles with Claude in order to establish specification documents and the technical stack we would use.

Core Principles

  • No frameworks, no build tools, no subscriptions
  • Accessible by default — WCAG AA minimum on every decision
  • Localization-ready from the start using Noto Sans
  • Performant — static files only
  • Scope-disciplined — ship simple, iterate later

Specs and Stack

Layer Tool Notes
Design Figma Utilize MCP to provide bridge between Figma and Claude Code
Code Editor VS Studio With Live Server extension for local preview
Version Control GitHub Repository to ensure safe iteration, and reference for project for Claude Code
Infrastructure HTML, CSS, JavaScript Plain — no frameworks or preprocessors
Hosting Netlify Free tier and allows multiple environments to test and secure release

Markdown Files

In earlier LLM expirements, I ran into slight hallucinations and or the models would infer and do thier own thing without guidance. Since then, I've read enough cautionary tales and workflow improvement articles from developers that informed how I would go forward with this project.

First step was to get out of singular chats and established a project within Claude and creating the Markdown (MD) files which would provide the support pillars.

The MD’s would grow over the months, adding methods to avoid the afformentioned issues, build development and process guardrails, contain best practices to avoid wasting tokens on specific tasks I could easily check myself, archive changes overtime, and note design intent.

Architecture and planning happened in Claude while implementation and Git operations were handled in Claude Code running in Visual Studio. The docs were utilized and referenced via prompts and were the only thing that had to survive the handoff between the two.

  • REFERENCE.md for project decisions and session handoffs
  • DESIGN-SYSTEM.md for design tokens
  • COMPONENTS.md for component specs
  • PROMPT-GUIDE.md to control what context got loaded per task type

Information Architecture

My initial goal was to build the following:

  • Home Page - containing selected work
  • About - containing more about me and my resume
  • Standard Page Template - for case studies

I decided on accessible Color, Spacing, Motion, picked a typeface (Noto Sans) for wider localization capabilities, had a decent set of Components made in Figma and a Standard Page template all working somewhat effectively in Desktop, Tablet, and Mobile breakpoints.

However, when you are developing a site that reflects your principles - you get nit picky, and you start to repeat “Not good enough” to yourself. And often push back on your own simplicity guardrails in favor of implementing something complex or even removing a feature after testing.

As a result of just having the basics - the site has taken longer than I wanted. I would see and reproduce a bug, and those bugs might have user experience issues that needed new solutions designed and tested. It also went through multiple partner reviews with my wife, who had some solid constructive criticism.

The Archive

The Archive is made of multiple key components:

  • The Database
  • Entries and their Tags
  • Search
    • Filter Drawer

The Database

To get around using a more complicated content manager, I opted for a lean singular static Json file. Every entry is referenced and Javascript fetches all entries or matches based on user search, sort and filtering. It is fast and efficient for what I need right now, but may need expansion later. As it stands, I don't have hundrens or thousands of entries to worry too much about performance but as a precaution, I made sure to implement a display cap.

Entries and Tags

Each entry contains a Hidden Primary 'Type' Tag (Work, Thoughts, etc.) - as well as Secondary 'Topic' Tags (Quality Assurance, User Experience, etc.) While the Primary Tags are hidden on the Entry Pages and their representative Card on the Archive - they both can be utilized by a user by accessing the Filter Drawer.

Search

While search is fully functional, it is currently dormant on the Archive. The reason for this is due to how I initially implemented the Search across devices.

Initially on Desktop it was at the top of page and if the user scrolled down, the Filter Drawer would appear. At the time, Search and Filters were all within the Drawer. This Drawer was also functional across Tablet and Mobile devices.

Now at the time, I was testing primarily through the Live Server via my Microsoft Edge Browser, shifting the response size based on device aspect ratios via the inspector. Judge me for using Edge all you like, but Edge's accessibility is top notch and it implemented Split Window prior to - and wayyyy better than - Chrome or Firefox...But things were working fine and as I had intended. Search functioned, Filters worked. My compact drawer was doing well...that is until I got out of the house.

After being proud of my implementation, I had set off biking to the store to pick up groceries. I was almost at the store when a gust of wind hit me in the face and provided me with the realization that I had forgotten to account for Virtual Keyboards.

As I picked out a good cabbage in the vegitable isle, it's sprinkler spritzed my face with cold water, and barely managed to wash away the embarressment I felt for forgetting something I see every single day.

Now back home, after putting away the groceries - I pushed changes and tested on my iPhoneSE2. (Again, judge me all you like, but I refuse to upgrade to a giant new impractical rectangle that doesn't fit into my pockets.)

As I tested, I saw the major issues I knew would be present.

Issue #1: the virtual keyboard envelopes half of the screenspace. And depending on the browser and its interpretation of fields - it also uses extra space.

Issue #2: Search fields Auto-zoom when active. Not only was the virtual keyboard resulting in a loss of space, a further loss of space was the resulting in a Zoom in on the Archives Body. If a user searched, the entries would be illegable.

While I fought for a day to redesign variants of the current implementations - I ultimatley made the decision to feature flag search until I find a cleaner solution and I had other issues to solve, features to implement, and bugs to fix. I went for another walk later that day to let it all go and trust myself enough to figure it out another day.

Filters

After removing the field, I was able to retain the structure and instead of a search field, I replaced it with text indicating the purpose of the drawer.

As I anticipated tag growth, I made sure the drawer would scale. Pagination was built into the drawer to ensure the user could parse the potential plethora of tags. If the user wants to Filter by a specific Primary Tag - the applicable entries with associated secondary tags will display, and the unrelated tags will be hidden.

Getting the Drawer to feel good across devices took some tweaking but as it sits right now - it's a solid little drawer.

Contents

The next major implementation, was the Floating and Collapsable Table of Contents.

When I had a Squarespace, this type of feature was gated behind a paywall. I had searched for templates but no luck. Then when I found a script some other squarespace user wrote - I was restricted as Code Injection was of course that higher tier. So this became a must for me as I wanted to the viewers of any entry to feel like they could navigate up and down the page with ease.
